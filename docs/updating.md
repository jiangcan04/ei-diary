# 更新自己的 ei ？

当前体验地址：https://ei-diary-check.pages.dev/ 。本轮准备v0.1.0，用户尚未验收本次真实更新，GitHub Release尚未发布。

## 更新前

在你平时使用的网址导出整本备份并保存到「文件」，核对文件可选回。记录当前网址、Git提交和Cloudflare成功部署。保持同一网址、数据库及Manifest身份；不要删除主屏幕图标或清除网站数据来更新。

## 自行部署者同步Fork

打开自己Fork的GitHub仓库，使用Sync fork → Update branch同步上游。如果提示冲突，先保留自己的修改并解决冲突，不直接丢弃。作者直接使用原仓库时不需要同步Fork。

本机开发者在GitHub Desktop选择正确仓库，Fetch origin后有更新则Pull；提交自己的变更并Push origin。下载ZIP不会自动更新已有Git仓库。远端提交才会触发Git集成部署，本地修改不会自动上线。

## 等待构建与部署

确认GitHub Actions全部通过，再在Cloudflare的Pages项目ei-diary-check查看最新main部署，核对提交号和成功状态。GitHub检查和Cloudflare自动部署各自运行，当前没有强制先检查后部署的门禁。失败时找第一条实际错误，不重复发布旧提交掩盖失败。

自己的Pages项目使用npm run build、dist输出，NODE_VERSION=26.10.0；具体见部署教程。原ei-ni-kan.pages.dev为Direct Upload，需按原流程上传构建产物，不能以为推送就会更新它。Workers旧站不作为本轮验收网址。

## 手机接受更新

先联网打开原网址。若新版已经等待，编辑期间更新按钮隐藏，应用不强制重载；完成当前操作，点保存，成功后返回月历，再点「更新应用」。刷新后等待「离线已就绪」。首次安装或已经是最新版本时可能没有更新按钮，不能仅凭按钮缺失判断失败。

保留一个旧版本已打开的标签页，在部署新版本后回到该标签页，才能检查等待更新的过程。若关闭了全部旧页面，新版可能直接激活。可在电脑网页源代码中查找application-version确认当前首页为0.1.0；这不是页面上的可见版本按钮。

Safari和主屏幕App分别检查。断网测试前，主屏幕App先联网成功打开一次。离线就绪只说明当前页面已被激活的Service Worker接管，不等于数据备份或跨设备同步。

## 第60步用户验收

1. 更新前保留测试混合页，并导出备份。保留旧版打开的页面。
2. 本地运行npm run typecheck、npm test、npm run build、npm run test:e2e；八项端到端测试应全部通过。
3. 推送本轮修改，核对GitHub检查和同一Pages网址的最新提交部署通过。
4. 旧页面仍在编辑时不强制刷新；保存返回后接受更新，原照片、笔迹、日期、页数正确，可继续编辑保存。
5. 从主屏幕联网打开完成准备后断网重开，确认手写字体、查看、编辑及保存可用。
6. 导出演示备份，在独立测试环境恢复，重复恢复不增页。保留原站，不清空日常数据作测试。
7. 核对package版本0.1.0、首页application-version、CHANGELOG与最终Release标签v0.1.0一致；附件需由同一发布提交构建。

当前结果：本轮以上各项待用户反馈，不沿用第59步结果冒充同网址更新通过。设备型号、系统、部署提交和日期随反馈补齐。第61步未开始。

## 回退代码

先导出当前备份，找到已知可用提交。通过新的还原提交并推送，或在平台确有可用回退入口时选择原网址的历史成功部署，等待结果并联网验证。Git集成后续推送仍会再次部署，不用删除项目重新创建网址。

代码回退不会撤销IndexedDB里的编辑或恢复已删除日记。备份恢复是按标识合并，冲突保留本机版本，也不是整库时间回滚；不要为了覆盖冲突而直接清空日记。未来若有数据结构升级，应先确认旧代码可兼容再回退。
